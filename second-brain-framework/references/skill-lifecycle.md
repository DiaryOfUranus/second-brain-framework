# 子 Skill 生命周期管理

> 来源：工程通论 §9.2-9.3, §9.8 + domain-skill-factory 流程
> 用法：当需要生成新 skill、追踪 skill 使用、审查迭代已有 skill 时加载。

## 生命周期总览

一个子 skill 的完整生命周期：

```
检测知识缺口 → 生成 skill → 安装 → 使用追踪 → 定期审查 → 迭代优化 →（退化则重写/退役）
```

每个阶段都有明确的质量门和完成标准。

## 阶段一：知识缺口检测

### 触发信号

在对话执行过程中，持续检测以下信号：

| 信号 | 说明 | 响应 |
|------|------|------|
| 用户进入新领域，无对应专用 skill | "我要做一个X，但没做过" | 触发生成流程 |
| 任务需要领域特定知识，已有 skill 不覆盖 | 需要了解"好"的标准、失败模式、最佳实践 | 触发生成流程 |
| 同类任务已出现3次以上，无系统化流程 | 反复手动执行相同步骤 | 触发模式提取 |
| 用户反复纠正同类错误 | 说明已有 skill 缺少相关教训 | 触发已有 skill 审查 |
| 已有 skill 的触发条件与实际使用不匹配 | skill 该触发时没触发，不该触发时触发了 | 触发已有 skill 审查 |

### 不触发的条件

- 任务是通用的，不需要领域特定知识（如"帮我算一下1+1"）
- 已有 skill 已覆盖且运行正常
- 任务太简单，不值得系统化（如一次性的小操作）
- 用户只要快速答案，不要系统方法

## 阶段二：子 Skill 生成

当检测到知识缺口时，执行以下8步流程。每步都有质量门，不通过不进入下一步。

### 步骤1：范围与约束确认

向用户确认（最多4个问题）：
1. **造物是什么？** — 要产出什么？（软件？文档？理论？游戏？流程？）
2. **责任等级？** — 做错了会怎样？（1=关键/安全，2=重要/业务，3=生产力/日常，4=个人/探索）
3. **硬约束？** — 不能碰什么？必须用什么？时间/预算限制？
4. **执行模式？** — 人主导AI辅助？AI主导人验收？纯AI？

**质量门**：四个问题都已回答。如果用户不确定，帮助决定，不带着模糊前进。

### 步骤2：知识需求评估

确定该领域需要什么知识：
1. **什么决定"好"？** — 列出3-6类所需知识
2. **是否已有结构化知识？** — 检查已有 skill、知识库、记忆文件。有 → 加载并跳到步骤4。无 → 继续步骤3。
3. **有什么信息源？** — 公开文档？用户提供的参考？训练数据？需要专家？

**质量门**：3-6个知识类别已列出，每个至少有一个已识别的信息源。

### 步骤3：工艺知识采集（自举）

这是核心步骤。在获取实现知识（怎么用工具）之前，先获取工艺知识（什么是好）。

**跳过此步直接实现 = #1 失败模式。**

按以下顺序获取（成本从低到高）：

**第一层：训练数据提取**
- 从训练数据中提取核心知识
- 每条标注"来自训练数据，未经验证"
- 聚焦：该领域从业者认为什么是优秀？已知失败模式有哪些？核心原则是什么？

**第二层：公开信息搜索**
- 搜索：行业标准、最佳实践、开源示例、学术论文、社区经验帖、教程
- 优先：权威来源 > 个人观点，近期 > 旧，实践经验 > 理论抽象
- 交叉验证：多个独立来源一致 → 置信度提升

**第三层：用户提供的参考**
- 读取用户提供的任何文件/文档
- 这是领域特定约定的最高权威来源

**穷尽以上三层后仍有缺口 → 向人请求补充。** "需要专家"不是默认选项，是穷尽公开获取后的剩余缺口。

将采集的知识结构化为文档：
- **核心原则**（5-8条，每条一句话+解释）
- **类型/子领域特定知识**（按子类型组织）
- **常见失败模式**（5-10条，每条含原因和预防方法）
- **设计/执行检查清单**

**质量门（验证测试）**：选一个已知优秀范例。能用这份知识解释它为什么好吗？能预测一个设计决策的好坏吗？不能 → 知识不足，回到采集。

### 步骤4：品质基准建立

这是**强制性质量门**。没有品质基准的 skill 不完整。

1. **找3-5个优秀范例**（从步骤3的采集中）
2. **分析为什么好** — 从接受者第一人称视角，不是设计者视角
3. **写体验标准** — "我[打开/开始/接触]后，[X秒/步]内[感受到/知道/能做到][Y]"
4. **竞品对比** — 已有最佳替代品是什么？我们的方案多给了什么？
5. **可检验最低标准** — 可勾选的检查项

**质量门（两项强制检查）**：

检查1 — **第一人称真实性**：读体验标准。它们是从用户/读者/玩家的视角写的吗？如果读起来像设计规格（"系统提供X功能"），改写为用户体验（"我坐下后，3秒内知道该干什么"）。

检查2 — **"为什么用我们的"测试**：如果"为什么用这个而不是已有替代品"的答案是"没有额外的，只是不同包装" → 标注并建议在找到真正增量价值前不要继续。

### 步骤5：执行手册生成

基于工艺知识（步骤3）和品质基准（步骤4），生成5-8步可执行 playbook。

每步格式：
```
## 步骤N：[步骤名]
**做什么：** 一句话
**怎么做：** 具体操作（3-5条）
**约束：** 本步骤的技术限制（如适用，只写上下文特定的）
**产出：** 本步骤的交付物
**完成标准：** 做到什么程度算完（可检验，不是"做好了"，是"X条件满足"）
**陷阱：** 常犯错误（1-3条）
**参考：** 知识库中的对应章节
```

生成原则：
- 步骤数：5-8步（太少=太粗，太多=太碎）
- 每步"完成标准"必须可检验
- 约束只写"上下文特定的"（不写通用语法，写"这个场景下用什么模式、避什么坑"）
- 第一步应该是"品质基准对照验证"

### 步骤6：Skill 组装

组装完整 skill 包：

```
[domain-name]-skill/
├── SKILL.md                          # 触发条件 + 执行手册 + 约束 + 工具声明
└── references/
    ├── [domain]-craft-knowledge.md  # 工艺知识（步骤3产出）
    ├── quality-benchmark.md          # 品质基准（步骤4产出）
    └── [domain]-failure-modes.md    # 常见失败模式（从步骤3提取）
```

SKILL.md 必须包含七部分：
1. YAML frontmatter（name, description, agent_created: true）
2. 禁止项（放最前面，风险优先）
3. 工具依赖声明
4. 触发条件
5. 执行手册（步骤5的产出）
6. 质量门（验收检查清单）
7. 参考文件指引

**质量门**：组装好的 skill 必须通过 `package_skill.py` 验证脚本。

### 步骤7：验证

**测试1：解释力测试**
- 选2个已知范例（一个优秀，一个平庸）
- 用 skill 的工艺知识分析两者
- 能解释为什么优秀的更好、平庸的更差吗？
- 不能 → 知识不足，回到步骤3

**测试2：预测力测试**
- 提出3个该领域的设计决策
- 用 skill 的原则预测每个决策的好坏
- 预测是否具体且可操作（不是"看情况"）？
- 预测模糊或矛盾 → 原则需要精炼

**质量门**：两项测试都通过。任一不通过 → 诊断缺口，回到对应步骤。

### 步骤8：安装与知识积累

**安装**：
- 用户级 skill → `~/.workbuddy/skills/`
- 项目级 skill → `.workbuddy/skills/`

**知识积累**（安装后持续执行）：
1. 追踪使用：哪些步骤用户经常 struggle
2. 捕获教训：用户纠正 AI 或说"这不行"时，记录
3. 定期审查：使用5-10次后审查（见阶段四）
4. 版本管理：每次修订更新版本号

## 阶段三：使用追踪

已有 skill 被使用时，持续追踪以下指标：

| 追踪维度 | 识别方法 | 响应 |
|---------|---------|------|
| 步骤说明不清晰 | 用户在某个步骤反复提问或出错 | 改写该步骤说明 |
| 知识缺口 | 实际使用中发现 skill 未覆盖的知识 | 补充到工艺知识文档 |
| 未预期的失败模式 | 遇到了失败模式清单中没有的问题 | 添加到失败模式文档 |
| 触发条件不匹配 | skill 该触发时没触发，或不该触发时触发了 | 调整 description 和触发条件 |
| 质量门不适用 | 某些质量门检查项在实际使用中无意义 | 修改质量门 |
| 工具/API过时 | skill 中引用的工具或API已更新或废弃 | 更新工具依赖 |

追踪方式：在每次对话的"自动提取"阶段（对话协议步骤5），如果本次对话使用了某个 skill，检查是否有需要记录的教训。

## 阶段四：定期审查与迭代

### 触发条件

满足以下任一条件时，触发 skill 审查：
- 某 skill 已被使用5-10次
- 用户明确要求"更新/优化某 skill"
- 发现 skill 中的信息过时或错误
- 在使用过程中发现 skill 未覆盖的重要场景
- 距上次审查已超过3个月

### 审查内容

1. **步骤说明审查**：每个步骤是否清晰？是否可检验？
2. **知识完整性审查**：是否有在使用中发现的未覆盖知识？
3. **失败模式审查**：是否有未预期的失败模式需要添加？
4. **品质基准审查**：品质基准是否仍然有效？是否有新的优秀范例需要参考？
5. **触发条件审查**：description 是否准确？触发词是否需要调整？
6. **工具依赖审查**：引用的工具/API/库是否仍然有效？
7. **质量门审查**：检查项是否仍然适用？是否需要增减？

### 迭代流程

1. 读取当前 skill 文件
2. 逐项审查（上述7项）
3. 识别需要修改的部分
4. 修改 skill 文件
5. 运行 `package_skill.py` 验证
6. 记录版本变更（主版本=框架大改，次版本=新模块，补丁=修正）

## 阶段五：退化诊断

### 退化信号

| 退化信号 | 严重程度 | 诊断 | 处理 |
|---------|---------|------|------|
| 工具/API信息过时 | 中 | 查阅最新文档 | 更新工具依赖部分 |
| 触发条件与实际不匹配 | 高 | 分析实际使用场景 vs description | 修改 description 和触发词 |
| 质量门检查项不再适用 | 中 | 分析为什么不再适用 | 修改或删除不适用的检查项 |
| 参考文档信息被证伪 | 高 | 找到证伪信息 | 修正错误信息，标注来源 |
| skill 长期未被使用（>3个月） | 低 | 判断是否仍有价值 | 标记"待审查"，审查后决定保留/退役 |
| skill 核心方法论被取代 | 高 | 评估新方法论 vs 旧方法论 | 重写或退役 |

### 退役流程

当一个 skill 确认不再需要时：
1. 确认没有其他 skill 依赖它
2. 将 skill 文件移到归档目录（不直接删除，以防需要恢复）
3. 在工作日志中记录退役原因
4. 如果 skill 中有可复用的知识，提取到知识库后再退役

## 跨项目复用协议

### 流程复用

执行手册、经验教训、品质基准模板 — 这些是跨项目复用的流程知识。

### 代码/组件复用

完成一个项目后，执行"模式提取"：
1. 识别项目中可复用的代码模式、工作流程、知识结构
2. 提取为可复用模式文档
3. 存入对应 skill 的参考文档或知识库
4. 新项目启动时，检查是否有可复用模式，有则直接加载

### 知识复用

- 工艺知识库是跨项目复用的（如游戏设计知识适用于所有游戏项目）
- 经验教训是跨项目复用的（如"API分批请求"适用于所有需要API的项目）
- 每次项目结束后，主动问："这个项目中有什么是下次可以复用的？"写入对应知识库
